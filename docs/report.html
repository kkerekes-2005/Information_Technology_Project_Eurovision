Eurovision Explorer
Project B report · Information Technology · Kinga Kerekes · 25 November 2026

1. Introduction

Domain. The Eurovision Song Contest is a yearly song competition between mostly European countries, held since 1956. Since 2004 most countries must pass a semi-final; the final is decided by the points the countries give each other, from juries, from the public, or since 2016 from both counted separately. Bookmakers publish odds before each show.

I turned a public dataset of the contest into a normalised PostgreSQL database, loaded it from Python in one transaction, answered questions about it in SQL and presented the answers in a Streamlit application. All analysis is done in SQL; Python only cleans the raw files during the load and passes query results to the charts.

3. Design

3.1 ER diagram

3.2 Relational model

Primary keys in bold, foreign keys in italics with the table they refer to.

  • COUNTRY (country_code, name)
  • CONTEST (year)
  • ROUND (round_id, year → CONTEST, round_type)
  • SONG_ENTRY (entry_id, year → CONTEST, country_code → COUNTRY, performer, song, place_contest, youtube_url, lyrics)
  • PERFORMANCE (entry_id → SONG_ENTRY, round_id → ROUND, running_order, place, points, points_tele, points_jury)
  • VOTE (round_id → ROUND, from_country → COUNTRY, to_country → COUNTRY, total_points, tele_points, jury_points)
  • PERSON (person_id, name)
  • ENTRY_CREDIT (entry_id → SONG_ENTRY, person_id → PERSON, role)
  • BOOKMAKER (bookmaker_id, name)
  • BETTING_ODDS (bookmaker_id → BOOKMAKER, entry_id → SONG_ENTRY, round_id → ROUND, odds)

Each entity became a table. The 1:N relationships became foreign keys on the N side; the N:N (many-to-many) relationships (performs in, is credited on) and the three-way relationships (votes for, quotes odds for) became tables whose primary key combines the keys they link. All tables are in third normal form; the source files were not (repeated country names, final and semi-final as two groups of columns, lists in one cell).

3.3 Justified exceptions

  1. Surrogate keys entry_id, round_id, person_id: (year, country) is not unique because of 1956, and song is empty in three rows. The natural combination is protected by a UNIQUE constraint.
  2. vote refers to countries, not entries: votes are cast by a country for a country; the entry is found through the year and the receiving country. This would be ambiguous only in 1956, which has no votes.
  3. total_points is stored although from 2016 it equals televote plus jury (P26): before 2016 the parts do not exist.
  4. place_contest and performance.points are stored: the overall place of semi-final entries cannot be derived, and points exist where votes are missing (1956, 2020, 2023 semi-finals).
  5. Self-vote rows are kept: removing them would be a filter outside SQL; a CHECK states they can only hold 0 points.
  6. contest has one column, so that rounds and entries of a year refer to one row and a year can exist before its rounds (Q13).

4.2 Schema

The schema is created first; the load only inserts rows. Types follow the profile: years, places and points SMALLINT (maximum 758), country codes VARCHAR(3) (because of wld), text sizes above the longest value found, odds NUMERIC(7,2), lyrics TEXT.

CREATE TABLE country (
    country_code VARCHAR(3)  PRIMARY KEY,
    name         VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE contest (
    year SMALLINT PRIMARY KEY CHECK (year >= 1956)
);

CREATE TABLE round (
    round_id   INTEGER     PRIMARY KEY,
    year       SMALLINT    NOT NULL REFERENCES contest (year),
    round_type VARCHAR(12) NOT NULL
               CHECK (round_type IN ('final', 'semi-final', 'semi-final-1', 'semi-final-2')),
    UNIQUE (year, round_type)
);

CREATE TABLE song_entry (
    entry_id      INTEGER      PRIMARY KEY,
    year          SMALLINT     NOT NULL REFERENCES contest (year),
    country_code  VARCHAR(3)   NOT NULL REFERENCES country (country_code),
    performer     VARCHAR(100) NOT NULL,
    song          VARCHAR(100),
    place_contest SMALLINT     CHECK (place_contest > 0),
    youtube_url   VARCHAR(100),
    lyrics        TEXT,
    UNIQUE (year, country_code, performer, song)
);

CREATE TABLE performance (
    entry_id      INTEGER  NOT NULL REFERENCES song_entry (entry_id),
    round_id      INTEGER  NOT NULL REFERENCES round (round_id),
    running_order SMALLINT CHECK (running_order > 0),
    place         SMALLINT CHECK (place > 0),
    points        SMALLINT CHECK (points >= 0),
    points_tele   SMALLINT CHECK (points_tele >= 0),
    points_jury   SMALLINT CHECK (points_jury >= 0),
    PRIMARY KEY (entry_id, round_id)
);

CREATE TABLE vote (
    round_id     INTEGER    NOT NULL REFERENCES round (round_id),
    from_country VARCHAR(3) NOT NULL REFERENCES country (country_code),
    to_country   VARCHAR(3) NOT NULL REFERENCES country (country_code),
    total_points SMALLINT   NOT NULL CHECK (total_points >= 0),
    tele_points  SMALLINT   CHECK (tele_points >= 0),
    jury_points  SMALLINT   CHECK (jury_points >= 0),
    PRIMARY KEY (round_id, from_country, to_country),
    CHECK (from_country <> to_country OR total_points = 0)
);

CREATE TABLE person (
    person_id INTEGER      PRIMARY KEY,
    name      VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE entry_credit (
    entry_id  INTEGER     NOT NULL REFERENCES song_entry (entry_id),
    person_id INTEGER     NOT NULL REFERENCES person (person_id),
    role      VARCHAR(10) NOT NULL CHECK (role IN ('composer', 'lyricist')),
    PRIMARY KEY (entry_id, person_id, role)
);

CREATE TABLE bookmaker (
    bookmaker_id INTEGER     PRIMARY KEY,
    name         VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE betting_odds (
    bookmaker_id INTEGER      NOT NULL REFERENCES bookmaker (bookmaker_id),
    entry_id     INTEGER      NOT NULL REFERENCES song_entry (entry_id),
    round_id     INTEGER      NOT NULL REFERENCES round (round_id),
    odds         NUMERIC(7,2) CHECK (odds >= 1),
    PRIMARY KEY (bookmaker_id, entry_id, round_id)
);

5. Queries

All queries were written by me (Kinga Kerekes). Each is a file in sql/queries/ with named parameters that the application binds to its filters; here the example values are written in. Required constructs: joins (Q01 and most others), GROUP BY with HAVING (Q02, Q03, Q04, Q06, Q10, Q12), subquery (Q03, Q13), window functions (Q04, Q05, Q07, Q09, Q11), CTE (Q04 to Q09, Q11), INSERT, UPDATE and DELETE in a transaction (Q13). Vote averages default to 1975 to 2015, when every country gave 1 to 12 points.

Q01. Which countries have won the contest most often, and when did each one last win?

Author: Kinga Kerekes. File: sql/queries/q01_wins_by_country.sql. Constructs: JOIN of four tables, GROUP BY, COUNT, MAX.

SELECT country.name AS country,
       COUNT(*) AS wins,
       MAX(song_entry.year) AS last_win
FROM performance
JOIN round ON round.round_id = performance.round_id
JOIN song_entry ON song_entry.entry_id = performance.entry_id
JOIN country ON country.country_code = song_entry.country_code
WHERE round.round_type = 'final'
  AND performance.place = 1
  AND song_entry.year BETWEEN 1957 AND 2023
GROUP BY country.country_code, country.name
ORDER BY wins DESC, last_win DESC;

Result: 27 rows. First 3:

country wins last_win
Sweden 7 2023
Ireland 7 1996
Netherlands 5 2019

Why it is meaningful: It ranks the countries by victories within any period, which shows who dominated which era of the contest.

Q02. Among the countries with at least a given number of finals, which have the best average place in the final?

Author: Kinga Kerekes. File: sql/queries/q02_best_average_place.sql. Constructs: JOIN, GROUP BY with HAVING, AVG, MIN.

SELECT country.name AS country,
       COUNT(*) AS finals,
       ROUND(AVG(performance.place), 2) AS average_place,
       MIN(performance.place) AS best_place
FROM performance
JOIN round ON round.round_id = performance.round_id
JOIN song_entry ON song_entry.entry_id = performance.entry_id
JOIN country ON country.country_code = song_entry.country_code
WHERE round.round_type = 'final'
  AND performance.place IS NOT NULL
GROUP BY country.country_code, country.name
HAVING COUNT(*) >= 20
ORDER BY average_place;

Result: 25 rows. First 3:

country finals average_place best_place
Italy 47 7.32 1
Monaco 21 7.38 1
Russia 22 7.68 1

Why it is meaningful: An average over many finals measures consistency instead of single victories, and HAVING removes countries with too few finals for the average to mean anything.

Q03. Which countries have taken part but never won, and how close did they come?

Author: Kinga Kerekes. File: sql/queries/q03_never_won.sql. Constructs: subquery with NOT IN, JOIN, GROUP BY, aggregates.

SELECT country.name AS country,
       COUNT(*) AS entries,
       MIN(song_entry.year) AS first_year,
       MIN(song_entry.place_contest) AS best_place
FROM country
JOIN song_entry ON song_entry.country_code = country.country_code
WHERE country.country_code NOT IN (
    SELECT song_entry.country_code
    FROM performance
    JOIN round ON round.round_id = performance.round_id
    JOIN song_entry ON song_entry.entry_id = performance.entry_id
    WHERE round.round_type = 'final'
      AND performance.place = 1
)
GROUP BY country.country_code, country.name
HAVING COUNT(*) >= 10
ORDER BY entries DESC;

Result: 20 rows. First 3:

country entries first_year best_place
Cyprus 40 1981 2
Malta 36 1971 2
Iceland 36 1986 2

Why it is meaningful: It separates the countries that are still waiting for a first victory from the winners, and shows how long and how nearly each has tried.

Q04. For a chosen country, which countries give it the most points on average in the final?

Author: Kinga Kerekes. File: sql/queries/q04_top_givers.sql. Constructs: two chained CTEs, GROUP BY with HAVING, RANK with PARTITION BY, top N per group.

WITH pair_average AS (
    SELECT vote.to_country,
           vote.from_country,
           COUNT(*) AS contests,
           ROUND(AVG(vote.total_points), 2) AS average_points
    FROM vote
    JOIN round ON round.round_id = vote.round_id
    WHERE round.round_type = 'final'
      AND vote.from_country <> vote.to_country
      AND round.year BETWEEN 1975 AND 2015
    GROUP BY vote.to_country, vote.from_country
    HAVING COUNT(*) >= 10
),
ranked AS (
    SELECT to_country, from_country, contests, average_points,
           RANK() OVER (
               PARTITION BY to_country
               ORDER BY average_points DESC
           ) AS rank_for_receiver
    FROM pair_average
)
SELECT giver.name AS giver,
       ranked.contests,
       ranked.average_points,
       ranked.rank_for_receiver
FROM ranked
JOIN country AS giver ON giver.country_code = ranked.from_country
WHERE ranked.to_country = 'se'
  AND ranked.rank_for_receiver <= 5
ORDER BY ranked.rank_for_receiver, giver.name;

Result: 5 rows. First 3:

giver contests average_points rank_for_receiver
Denmark 33 8.00 1
Norway 38 7.24 2
Estonia 20 6.65 3

Why it is meaningful: It reveals the stable voting friends of a country; the period 1975 to 2015 is used because every country then gave the same 1 to 12 points, so the averages are comparable.

Q05. How did the final place of a country change from each of its finals to the next?

Author: Kinga Kerekes. File: sql/queries/q05_place_over_time.sql. Constructs: two chained CTEs, LAG.

WITH finals AS (
    SELECT song_entry.year,
           song_entry.performer,
           performance.place
    FROM performance
    JOIN round ON round.round_id = performance.round_id
    JOIN song_entry ON song_entry.entry_id = performance.entry_id
    WHERE round.round_type = 'final'
      AND performance.place IS NOT NULL
      AND song_entry.country_code = 'se'
),
with_previous AS (
    SELECT year, performer, place,
           LAG(place) OVER (ORDER BY year) AS previous_place
    FROM finals
)
SELECT year, performer, place, previous_place,
       previous_place - place AS places_gained
FROM with_previous
ORDER BY year;

Result: 61 rows. First 3:

year performer place previous_place places_gained
1958 Alice Babs 4
1959 Brita Borg 9 4 -5
1960 Siw Malmkvist 10 9 -1

Why it is meaningful: The difference with the previous final shows the rises and falls of a country over the years, which a list of places alone hides.

Q06. Which pairs of countries give each other high points in both directions?

Author: Kinga Kerekes. File: sql/queries/q06_mutual_voting.sql. Constructs: CTE joined with itself, GROUP BY with HAVING.

WITH pair_average AS (
    SELECT vote.from_country,
           vote.to_country,
           COUNT(*) AS contests,
           ROUND(AVG(vote.total_points), 2) AS average_points
    FROM vote
    JOIN round ON round.round_id = vote.round_id
    WHERE round.round_type = 'final'
      AND vote.from_country <> vote.to_country
      AND round.year BETWEEN 1975 AND 2015
    GROUP BY vote.from_country, vote.to_country
    HAVING COUNT(*) >= 10
)
SELECT first_country.name AS country_a,
       second_country.name AS country_b,
       a_to_b.average_points AS a_gives_b,
       b_to_a.average_points AS b_gives_a,
       a_to_b.contests AS contests
FROM pair_average AS a_to_b
JOIN pair_average AS b_to_a
  ON b_to_a.from_country = a_to_b.to_country
 AND b_to_a.to_country = a_to_b.from_country
JOIN country AS first_country ON first_country.country_code = a_to_b.from_country
JOIN country AS second_country ON second_country.country_code = a_to_b.to_country
WHERE a_to_b.from_country < a_to_b.to_country
  AND a_to_b.average_points >= 6
  AND b_to_a.average_points >= 6
ORDER BY a_to_b.average_points + b_to_a.average_points DESC;

Result: 3 rows. First 3:

country_a country_b a_gives_b b_gives_a contests
Cyprus Greece 11.11 10.24 27
Russia Ukraine 6.92 8.67 12
Bosnia & Herzegovina Croatia 7.21 8.00 14

Why it is meaningful: A high average in both directions over many contests is the pattern known as bloc voting, which a single generous vote cannot produce.

Q07. In the finals since 2016, how did the televote rank and the jury rank of each entry differ?

Author: Kinga Kerekes. File: sql/queries/q07_jury_vs_televote.sql. Constructs: JOIN, two RANK window functions with PARTITION BY, arithmetic.

WITH ranked AS (
    SELECT song_entry.year,
           country.name AS country,
           song_entry.performer,
           performance.points_tele,
           performance.points_jury,
           RANK() OVER (
               PARTITION BY song_entry.year
               ORDER BY performance.points_tele DESC
           ) AS tele_rank,
           RANK() OVER (
               PARTITION BY song_entry.year
               ORDER BY performance.points_jury DESC
           ) AS jury_rank
    FROM performance
    JOIN round ON round.round_id = performance.round_id
    JOIN song_entry ON song_entry.entry_id = performance.entry_id
    JOIN country ON country.country_code = song_entry.country_code
    WHERE round.round_type = 'final'
      AND performance.points_tele IS NOT NULL
      AND performance.points_jury IS NOT NULL
      AND song_entry.year BETWEEN 2016 AND 2023
)
SELECT year, country, performer, points_tele, points_jury,
       tele_rank, jury_rank,
       jury_rank - tele_rank AS public_favoured_by
FROM ranked
WHERE jury_rank - tele_rank >= 15
   OR tele_rank - jury_rank >= 15
ORDER BY year, tele_rank;

Result: 16 rows. First 3:

year country performer points_tele points_jury tele_rank jury_rank public_favoured_by
2016 Poland Michał Szpak 222 7 3 25 22
2016 Austria Zoë 120 31 8 24 16
2016 Malta Ira Losco 16 137 21 4 -17

Why it is meaningful: Ranking each entry twice inside its own year shows which songs the public loved and the juries did not, and the reverse, independent of how many points were available.

Q08. Which countries of the database have never appeared in a final, and how many entries did they send?

Author: Kinga Kerekes. File: sql/queries/q08_never_in_a_final.sql. Constructs: CTE, two LEFT JOIN, IS NULL, COUNT(column) after a LEFT JOIN.

WITH finalists AS (
    SELECT DISTINCT song_entry.country_code
    FROM performance
    JOIN round ON round.round_id = performance.round_id
    JOIN song_entry ON song_entry.entry_id = performance.entry_id
    WHERE round.round_type = 'final'
)
SELECT country.name AS country,
       COUNT(song_entry.entry_id) AS entries,
       MIN(song_entry.year) AS first_year,
       MAX(song_entry.year) AS last_year
FROM country
LEFT JOIN finalists ON finalists.country_code = country.country_code
LEFT JOIN song_entry ON song_entry.country_code = country.country_code
WHERE finalists.country_code IS NULL
GROUP BY country.country_code, country.name
ORDER BY entries DESC;

Result: 2 rows. First 3:

country entries first_year last_year
Andorra 6 2004 2009
Rest of the World 0

Why it is meaningful: The LEFT JOIN keeps the countries without a match, so it finds both the country that always failed in the semi-finals and the voting-only code that never sent a song.

Q09. How did the number of top finishes of chosen countries accumulate over the years?

Author: Kinga Kerekes. File: sql/queries/q09_cumulative_top_places.sql. Constructs: CTE, running total with SUM OVER, PARTITION BY and ORDER BY, list parameter with ANY.

WITH top_finishes AS (
    SELECT country.name AS country,
           song_entry.year,
           COUNT(*) AS top_finishes
    FROM performance
    JOIN round ON round.round_id = performance.round_id
    JOIN song_entry ON song_entry.entry_id = performance.entry_id
    JOIN country ON country.country_code = song_entry.country_code
    WHERE round.round_type = 'final'
      AND performance.place <= 5
      AND song_entry.country_code = ANY(ARRAY['se', 'ie', 'gb', 'ua'])
    GROUP BY country.name, song_entry.year
)
SELECT country, year,
       SUM(top_finishes) OVER (
           PARTITION BY country
           ORDER BY year
       ) AS cumulative_top_finishes
FROM top_finishes
ORDER BY country, year;

Result: 83 rows. First 3:

country year cumulative_top_finishes
Ireland 1966 1
Ireland 1967 2
Ireland 1968 3

Why it is meaningful: A running total turns isolated good results into a curve, so periods of success and long droughts of each country become visible and comparable.

Q10. Is the position in the running order of the final related to the result?

Author: Kinga Kerekes. File: sql/queries/q10_running_order.sql. Constructs: JOIN, GROUP BY with HAVING, AVG, MIN.

SELECT performance.running_order,
       COUNT(*) AS performances,
       ROUND(AVG(performance.place), 2) AS average_place,
       MIN(performance.place) AS best_place
FROM performance
JOIN round ON round.round_id = performance.round_id
WHERE round.round_type = 'final'
  AND performance.place IS NOT NULL
  AND performance.running_order IS NOT NULL
  AND round.year BETWEEN 2004 AND 2023
GROUP BY performance.running_order
HAVING COUNT(*) >= 10
ORDER BY performance.running_order;

Result: 26 rows. First 3:

running_order performances average_place best_place
1 19 15.95 5
2 19 20.05 6
3 19 13.63 2

Why it is meaningful: If the order did not matter the average place would be the same for every position; a better average for late positions supports the common belief that performing late helps.

Q11. How well did the bookmakers predict the final: where did their favourites finish?

Author: Kinga Kerekes. File: sql/queries/q11_bookmakers.sql. Constructs: two chained CTEs, AVG, RANK with PARTITION BY, JOIN of five tables.

WITH average_odds AS (
    SELECT betting_odds.entry_id,
           betting_odds.round_id,
           COUNT(betting_odds.odds) AS bookmakers,
           ROUND(AVG(betting_odds.odds), 2) AS average_odds
    FROM betting_odds
    JOIN round ON round.round_id = betting_odds.round_id
    WHERE round.round_type = 'final'
      AND round.year BETWEEN 2015 AND 2023
    GROUP BY betting_odds.entry_id, betting_odds.round_id
),
ranked AS (
    SELECT entry_id, round_id, bookmakers, average_odds,
           RANK() OVER (
               PARTITION BY round_id
               ORDER BY average_odds
           ) AS odds_rank
    FROM average_odds
)
SELECT song_entry.year,
       country.name AS country,
       song_entry.performer,
       ranked.bookmakers,
       ranked.average_odds,
       ranked.odds_rank,
       performance.place AS real_place
FROM ranked
JOIN performance ON performance.entry_id = ranked.entry_id
                AND performance.round_id = ranked.round_id
JOIN song_entry ON song_entry.entry_id = ranked.entry_id
JOIN country ON country.country_code = song_entry.country_code
WHERE performance.place IS NOT NULL
  AND ranked.odds_rank <= 3
ORDER BY song_entry.year, ranked.odds_rank;

Result: 24 rows. First 3:

year country performer bookmakers average_odds odds_rank real_place
2015 Sweden Måns Zelmerlöw 19 2.08 1 1
2015 Russia Polina Gagarina 19 4.14 2 2
2015 Italy Il Volo 19 5.42 3 3

Why it is meaningful: Comparing the rank given by the average odds with the real place tests whether the betting market is a reliable forecast of the contest.

Q12. Which composers have written the most entries, and how did their songs do?

Author: Kinga Kerekes. File: sql/queries/q12_composers.sql. Constructs: JOIN through the N:N table entry_credit, GROUP BY with HAVING, aggregates.

SELECT person.name AS composer,
       COUNT(*) AS entries,
       COUNT(DISTINCT song_entry.country_code) AS countries,
       MIN(song_entry.year) AS first_year,
       MAX(song_entry.year) AS last_year,
       MIN(song_entry.place_contest) AS best_place
FROM person
JOIN entry_credit ON entry_credit.person_id = person.person_id
JOIN song_entry ON song_entry.entry_id = entry_credit.entry_id
WHERE entry_credit.role = 'composer'
GROUP BY person.person_id, person.name
HAVING COUNT(*) >= 6
ORDER BY entries DESC, best_place;

Result: 12 rows. First 3:

composer entries countries first_year last_year best_place
Ralph Siegel 23 4 1974 2017 1
Thomas G:son 15 7 2001 2023 1
Dimitris Kontopoulos 11 6 2007 2021 2

Why it is meaningful: It identifies the professional songwriters behind many entries, often for several countries, who are invisible in a list of performers.

Q13. How is a new contest registered so that either all of its rows are saved or none?

Author: Kinga Kerekes. File: sql/queries/q13_new_contest_transaction.sql. Constructs: INSERT, UPDATE and DELETE inside BEGIN ... COMMIT, a failed statement followed by ROLLBACK.

--
-- Run each part separately in the pgAdmin Query Tool: select the part and press F5.
-- The ids 104 and 1720 are the next free ones: the load ends at round 103 and entry 1719.
-- The 2024 winner is used as the example (source: eurovisionworld.com/eurovision/2024,
-- checked on 2026-11-15: 591 points, 226 public, 365 jury, running order 21).
-- Part 3 removes it again, so the database ends exactly as the dataset delivered it.

-- Part 1. Register the 2024 contest, its final, the winning entry and its result.
BEGIN;
INSERT INTO contest (year) VALUES (2024);
INSERT INTO round (round_id, year, round_type) VALUES (104, 2024, 'final');
INSERT INTO song_entry (entry_id, year, country_code, performer, song, place_contest)
VALUES (1720, 2024, 'ch', 'Nemo', 'The Code', 1);
INSERT INTO performance (entry_id, round_id, running_order, place, points, points_tele, points_jury)
VALUES (1720, 104, 21, 1, 591, 226, 365);
COMMIT;

-- Check: the four rows are there.
SELECT song_entry.year, country.name, song_entry.performer, song_entry.song,
       performance.place, performance.points
FROM performance
JOIN song_entry ON song_entry.entry_id = performance.entry_id
JOIN country ON country.country_code = song_entry.country_code
WHERE song_entry.year = 2024;

-- Part 2. A transaction that fails halfway. The UPDATE and the first vote are valid.
-- The second vote is Switzerland giving itself 12 points, which the CHECK constraint rejects.
BEGIN;
UPDATE performance SET running_order = 22 WHERE entry_id = 1720 AND round_id = 104;
INSERT INTO vote (round_id, from_country, to_country, total_points) VALUES (104, 'se', 'ch', 12);
INSERT INTO vote (round_id, from_country, to_country, total_points) VALUES (104, 'ch', 'ch', 12);
COMMIT;

-- After the error PostgreSQL ignores every statement until the transaction ends. End it:
ROLLBACK;

-- Check: the valid changes were undone too. running_order is still 21 and there are no votes.
SELECT performance.running_order,
       (SELECT COUNT(*) FROM vote WHERE round_id = 104) AS votes_in_round_104
FROM performance
WHERE entry_id = 1720 AND round_id = 104;

-- Part 3. Remove the 2024 contest again. Children first, because of the foreign keys.
BEGIN;
DELETE FROM performance WHERE round_id = 104;
DELETE FROM song_entry WHERE entry_id = 1720;
DELETE FROM round WHERE round_id = 104;
DELETE FROM contest WHERE year = 2024;
COMMIT;

-- Check: no rows are left for 2024.
SELECT COUNT(*) AS contests_2024 FROM contest WHERE year = 2024;

Result: run by hand in pgAdmin, one part at a time. Part 1 inserts 4 rows. Part 2 stops with a CHECK violation on vote and, after ROLLBACK, the check shows running_order 21 and 0 votes. Part 3 deletes the 4 rows.

Why it is meaningful: A contest is only usable when its year, round, entry and result exist together; the transaction guarantees that a failure halfway never leaves a contest without its rows.

Q14. In which decades do the lyrics most often contain a given word?

Author: Kinga Kerekes. File: sql/queries/q14_word_in_lyrics.sql. Constructs: LEFT JOIN of a table with itself, LIKE with a parameter, COUNT(*) against COUNT(column), GROUP BY on an expression.

SELECT all_entries.year / 10 * 10 AS decade,
       COUNT(*) AS entries_with_lyrics,
       COUNT(matching.entry_id) AS entries_with_word,
       ROUND(100.0 * COUNT(matching.entry_id) / COUNT(*), 1) AS percent
FROM song_entry AS all_entries
LEFT JOIN song_entry AS matching
       ON matching.entry_id = all_entries.entry_id
      AND LOWER(matching.lyrics) LIKE '%love%'
WHERE all_entries.lyrics IS NOT NULL
GROUP BY all_entries.year / 10 * 10
ORDER BY decade;

Result: 8 rows. First 3:

decade entries_with_lyrics entries_with_word percent
1950 43 4 9.3
1960 163 16 9.8
1970 176 30 17.0

Why it is meaningful: The share of entries whose lyrics contain a word shows how a theme or a language rose and fell over the decades; the share is used because the number of entries per decade grew a lot.

6. Visualization

The application (app/streamlit_app.py, look in app/style.py) has five tabs with eight charts and seven tables. It connects through src/db.py, whose run_query(sql, params) sends a query file with SQLAlchemy text() and bound parameters and returns the rows.

  • Charts use only SQL results: each chart draws the returned rows in their order; a chart with several countries (Q09) runs its query once per country. A Data and SQL panel under each chart shows the rows and the query.
  • Filters are parameters: sliders, menus and number boxes send their values as bound parameters; menus and limits come from queries in sql/app/.
  • No crashes: inputs have fixed limits; every query runs inside fetch(), which shows a message on error; empty results are explained.
  • No SQL injection: the only free text, the lyrics search, is sent as a LIKE parameter with % and _ escaped.
